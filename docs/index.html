Portfolio project · AI hiring pipeline + compliance

An AI resume screener that audits itself for bias — before you ship it.

Most "AI resume screener" side projects stop at matching keywords to a job description. FairHire AI adds the piece that actually matters to an employer: it runs the exact statistical test regulators use — the EEOC's four-fifths rule and NYC Local Law 144's bias-audit requirement for Automated Employment Decision Tools — against its own recommendations.

Why this project exists

The one-sentence pitch: a hiring AI's accuracy and its legal exposure should be measured together, not separately — this project does both, end to end, in one pipeline.

NYC Local Law 144 (in effect since 2023, actively enforced in 2026) requires employers to commission an independent bias audit before using an AEDT on candidates, publish the results, and give candidates notice. The underlying math — selection rate by demographic group, impact ratio, flagged if under 80% — is exactly what backend/bias_audit.py implements. Building that logic, rather than just wrapping an LLM in a chat box, is what separates this from a weekend "ChatGPT resume matcher."

Architecture

Scoring and auditing are deliberately two independent modules joined only at the end — the way a real compliance pipeline has to work.

Resume text

Unstructured .txt input, one per candidate

→

ai_service.parse_resume()

Structured JSON: skills, years, education

→

ai_service.score_candidate()

0–100 fit score + rationale, qualifications only

Job description

Parsed into required / preferred skills, min years

→

+ EEO group label

Collected separately, never seen by the scorer

→

bias_audit.run_four_fifths_audit()

Selection rate, impact ratio, flagged groups

Demographic data is joined to results only after scoring, for audit purposes — mirroring how real EEO self-identification data is collected separately from applications. An AI system that infers race or gender from a résumé to "check for bias" would itself be a bias risk.

Design decisions worth explaining in an interview

1Demographic data never touches the scoring model

It's joined to results only afterward, for audit purposes. An AI system that infers race/gender from a résumé to "check for bias" would itself be a bias risk.

2The audit module doesn't know what produced the scores

It takes any list of {group, selected} and audits it — reusable against a completely different scoring method without touching this file, a common ask in real MLOps/compliance work.

3Structured output, not chat

Every LLM call returns a fixed, validated JSON schema. The difference between "I used the ChatGPT API" and "I built an LLM into a software pipeline."

4Offline demo mode by design

Not an afterthought — it's what lets this ship as a fully working, testable project with no API key, and it's a realistic local-dev pattern for any paid API.

Quickstart

Works immediately with no API key. Set ANTHROPIC_API_KEY later to switch the same code path to live Claude calls.

git clone https://github.com/johnsonjamesr02-png/fairhire-ai.git
cd fairhire-ai
pip install -r requirements.txt

# Runs the full pipeline end-to-end, offline, no key needed:
python scripts/run_demo.py

# Run the unit tests:
python -m pytest tests/ -v

# For live Claude API scoring instead of the demo stand-in:
export ANTHROPIC_API_KEY=your-key-here
python scripts/run_demo.py

# Run the API + local dashboard:
cd backend && uvicorn main:app --reload --port 8000
# then open frontend/index.html in a browser

Full endpoint docs, module-by-module breakdown, and the complete architecture diagram are in the project README.

Honest limitations

  • The demo-mode scorer is simple keyword/years matching — a stand-in for the LLM, not a claim that keyword matching is good hiring practice. Real scoring happens through Claude when ANTHROPIC_API_KEY is set.
  • Eight synthetic candidates is enough to exercise the math and unit tests, not enough to be statistically meaningful — a real audit needs a real applicant pool.
  • This is a personal/portfolio project, not a compliance product. A real AEDT bias audit must be conducted by an independent auditor under Local Law 144 — this demonstrates understanding of that requirement, it doesn't satisfy it.

Roadmap ideas

  • Real embeddings similarity as a second signal alongside the LLM score, replacing keyword skill-matching in demo mode.
  • Intersectional group analysis (e.g. Black women vs. all others), which Local Law 144 audits require alongside single-category analysis.
  • Persisted run history so selection rates can be tracked over time, not just per-run.
